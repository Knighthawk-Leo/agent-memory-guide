Adding agent memory to the ROS pipeline

We read the source of Hindsight and OpenViking, and mapped the ROS workflow engine, to answer three questions: how each tool works inside, how it would plug into ROS, and how agent memory sits next to the knowledge base, the code index and RAG that ROS already runs.

Hindsight Integrate

MIT licence, Postgres + pgvector, native OpenRouter support, async Python client, built-in MCP. It fills the gap ROS has today: learning from past Claude Code runs.

OpenViking Not now

AGPLv3, single node by default, cannot use our pgvector or Qdrant. Its strength is code and document context, which overlaps with the VectorMCP code index ROS already has.

When sources disagree

Give the agent a fixed order of trust in its system prompt:

  1. Rules in CLAUDE.md and memory blocks. People reviewed them.
  2. Current code from the code index or the checked-out repo. It is what will actually run.
  3. Active decisions in memory (kind:decision, status active).
  4. Knowledge base documents. Useful intent, may lag the code.
  5. Learned memory from past runs. Treat as hints; verify against the code before acting.

How knowledge moves between them

Memory is where new knowledge lands first. Some of it earns a permanent place:

  1. A run finishes. Its tool calls, failures and fixes are retained into memory with run scope.
  2. Hindsight consolidates repeated facts into observations with a proof count.
  3. A lesson seen across several runs is proposed for promotion in the ROS memory UI.
  4. A reviewer moves it into CLAUDE.md, a memory block or the knowledge base.
  5. When the code changes and a memory contradicts it, the memory is invalidated.
02 · What ROS already has

Most of the retrieval stack is already built

ROS runs FastAPI with an arq worker, Postgres with pgvector, and a Qdrant-backed code index. It already has a knowledge base, archival memory and memory blocks. What it lacks is memory that learns from Claude Code runs.

Knowledge baseIngest, hybrid BM25 + vector search with RRF, reranking, QA pairs.services/knowledge.py · knowledge/store.py · pgvector_store.py
Code indexVectorMCP on Qdrant, exposed to Claude Code over MCP: route_task, search_code, get_file, expand_context.services/code_index.py · VectorMCP/codeindex/mcp_server.py
Archival memoryremember / recall over a memories table and a ros_mem_<dim> vector collection.services/memory.py
Memory blocksLetta-style, versioned blocks per user and per agent. Up to 8 per scope.services/memory_blocks.py
Sleep-time consolidationPost-run consolidation, behind ROS_MEMORY_SLEEPTIME_ENABLED.services/memory_consolidation.py
Decision log & activityClaude Code runs record decisions, tool activity, diffs and progress cards on spans.nodes/claude_code.py · nodes/claude_decisions.py

Gaps in the Claude Code node

GapThe claude_code node does not inject user or agent memory blocks. Only the generic agent node does (agent_node.py:678-686).
GapClaude Code has no tool to write memory. The memory directive only says "if a shared-memory tool is available".
GapThe full transcript is not kept. Only the SDK session_id and a bounded activity summary are stored.
GapUpstream SystemMessages (from retrieval or code_index nodes) never reach Claude Code: it reads only the last human message. Context must travel through a state key or be injected inside the node.
Fix first. The current feat/codebase-indexing HEAD (77fdf58) does not start. The merge duplicated the CodeRepo model (entities.py:617 and :659), so importing ros.models fails. claude_code.py:1753 also passes arguments that _materialize_context_docs does not accept. services/code_index.py and the code-index MCP wiring in services/runtime.py are duplicated too.
A design decision to make. The ROS design doc sdlc-memory-topology.md lists "no new general-purpose agent memory store" as an anti-goal. Hindsight should therefore replace the archival memory path behind the existing MemoryService interface over time, not run as a second store forever.
03 · Hindsight, from the source

Retain, recall, reflect

Hindsight is a FastAPI server on port 8888 backed by Postgres and pgvector. Memory lives in banks. Each write is run through an LLM that extracts facts, entities and links. A background job merges related facts into observations. Pick an operation to see what happens inside.

MITlicence
~36kstars
1–3 wkrelease cadence
384-dbge-small embeddings by default
openrouternative LLM provider
The four memory types are world facts, experience (what the agent itself did), observation (consolidated in the background, with a proof count) and mental models (a saved question whose answer is regenerated). The "opinion" network in older docs has been removed from the code.
No auth by defaultREST and MCP are open until you set the tenant extension. The built-in option is one shared API key.
Filter with tags, not metadataRecall filters only on tags. Metadata values must be strings. The default tags_match="any" also returns untagged memories, so use any_strict.
document_id replacesRe-using a document id deletes the old facts. Use one id per run, or update_mode="append".
An LLM call on every writeEach retain runs extraction; consolidation is another call; reflect loops up to 10 times. Use retain_async, a cheaper retain model and batching.
Eventually consistentObservations and mental models update in the background, so a recall right after a retain may not see it.
Fixed embedding sizeThe dimension is set in the schema. Changing embedding model on a populated database fails at startup.
04 · OpenViking, from the source

A filesystem of context with three levels of detail

OpenViking stores resources, memories and skills under viking:// URIs. At ingest, an LLM writes a short abstract (L0) and an overview (L1) for every directory; L2 is the original file. Click a node to read its tiers, and switch the search mode to see how retrieval walks the tree.

AGPLv3licence
~39kstars
64releases in 8 months

LiteLLMneeded for Claude
Query: "where is the JWT verified?"
Recursive search needs a rerankerfind() is always one flat vector search. search() only walks the directory tree when a rerank model is configured.
Single node by defaultThe local vector engine takes an exclusive lock on the workspace. Scaling out needs VikingDB or the commercial edition.
Its own vector storeBackends are its embedded C++ engine, VikingDB or openGauss. It cannot use the pgvector or Qdrant that ROS runs.
Coding memory is offThe cases, trajectories and experiences memory types sit behind a global switch that defaults to off. Default types are profile, preferences, entities, events.
AGPLv3Running a modified server as a network service triggers copyleft terms. Needs legal review.
Code indexingCode files get a tree-sitter skeleton with no LLM call; docs cost one LLM call each, plus one per directory. Files are embedded whole, capped at 4,096 tokens.

06 · Wiring Hindsight into ROS

Six changes, following one run

A run starts from Slack, compiles on the API, executes on an arq worker or a VM, and finalizes back on the API. Memory touches it at six points. Click a step for the file locations and a code sketch.

Banks and scopes

Orgbank t{tenant}__org
Company-wide conventions. Written only by promotion.
Repobank t{tenant}__{repo}
One bank per repository. Recall filters on scope:repo.
Usertag user:{id}
Preferences of the person who triggered the run, from Thread.meta["end_user"].
Runtags run:{id} scope:run
Everything a run writes. Not recalled by default until promoted.
07 · Rollout

Ship it in small steps, measure each one

Phase 0
Unblock the branch

Remove the duplicate CodeRepo model, the duplicated code_index.py module and MCP wiring, and fix the _materialize_context_docs call.

Done whenapi and worker start; a claude_code run completes.
Phase 1
Shadow writes

Deploy Hindsight on the existing Postgres server. Write back after each run (step 5). No recall yet. Persist transcripts.

Done whenTwo weeks of runs retained; LLM cost per run known; memories read sensibly.
Phase 2
Recall at start, one workflow

Turn on steps 2 and 3 for one workflow. Compare with and without memory on the same tasks.

Done whenFewer turns or failed commands per run, no rise in wrong edits.
Phase 3
MCP pull, reflect and promotion

Attach the Hindsight MCP server with read-only tools. Add post-run reflection and a promotion queue in the memory UI.

Done whenReviewers promote lessons weekly; stale memories get invalidated.
Phase 4
One memory path

Move MemoryService archival memory onto Hindsight behind the same interface, in line with the design doc's anti-goal.

Done whenOne store for learned memory; memory blocks stay for always-on rules.
Before committing. Replay 50 to 100 real ROS run traces through Hindsight and a plain pgvector baseline built on the existing MemoryService. Public benchmarks measure chat recall, not coding.
