Research brief · September 2026

How coding agents remember what they learned

A coding agent starts every session with no memory of the last one. A memory layer captures what it did, stores it, and hands the useful parts back next time. We compared 12 memory systems and worked out how to run one for a pipeline shared across a whole organization.

02 · How is this different from Claude Code's memory files?

Load everything, or search for what matters

Claude Code ships two memory files: CLAUDE.md holds rules people write, and auto memory holds notes Claude writes for itself. Both load in full at the start of every session. A memory service stores far more and loads only the items that match the current task.

04 · Can we update or overwrite a previous decision?

What happens to the old decision

Every system lets you change a decision. They differ in what they keep. Pick a strategy and apply the same change to see the difference: the team switched from jsonwebtoken to jose.

Our recommendation: never overwrite

Store each decision as a record, in the style of an Architecture Decision Record. Search returns only active decisions by default. The history stays available for "why did we switch?"

id: dec-042
decision: "Use jose instead of jsonwebtoken"
status: active            # active | superseded
supersedes: dec-017
author: user@org
commit: a1b2c3d
reason: "Edge runtime compatibility"
05 · How do parallel agents avoid colliding?

Git and the orchestrator keep work correct. Memory keeps agents informed.

None of these memory tools offers locking or task ownership. When several agents work at once, collisions are prevented by how the work is split and merged. Memory's job is to let each agent see what the others are doing.

Press play to run three agents on one feature.
Split by ownershipThe planner gives each subtask the files it owns, plus read-only interfaces. Overlapping files run one after another, or merge into one task.
Isolate with git worktreesEach run gets its own worktree and branch. Changes come back only through merges.
Enforce with leasesA lease table in Postgres or Redis records which agent holds which path, and until when. A pre-commit check rejects writes outside held paths.
Share a work ledgerBefore building a helper, an agent searches the ledger ("is anyone building a retry wrapper?") and registers its own work.
Define contracts firstInterfaces, types and API stubs are merged before fan-out. Agents code against a fixed contract.
Integrate in a final stepOne agent or CI job merges branches, resolves conflicts, runs the full test suite and scans for near-duplicate code.
Write memory narrowly during runsParallel runs write to run scope. Only the integration step promotes verified learnings to repo or org scope.
06 · How are tool calls stored, and why bother?

From a raw log to a lesson the next run can use

Every command an agent runs produces a record: the tool, its arguments, the output and the exit code. Memory systems compress that record into a short observation, index it for search, and keep the raw log as evidence.

07 · Recommendation

What we'd run for an org-shared coding pipeline on VMs

Two kinds of memory, kept separate. Curated knowledge that people review like code, and learned knowledge that agents build up as they work.

Always-on rules
A short CLAUDE.md per repo: commands, conventions, hard rules. Loaded in full every session.
CLAUDE.md
Curated repo knowledge
A git-backed context tree of architecture notes and decisions, changed through reviewed pull requests.
Letta / ByteRover style
Learned & episodic memory
What agents discovered while working: failures, fixes, procedures. Self-hosted on Postgres, searched per task.
Hindsight
Alternatives
Graphiti when you must audit "what was true when". Mem0 when you want a managed service and a large ecosystem.
